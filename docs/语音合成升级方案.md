# 宝贝学习乐园 · 专业级语音合成升级方案

> 目标：把当前「机械、缺乏自然度」的朗读，升级为**设备端 AI 模型驱动、可离线、可控情感与韵律**的专业级语音。
> 范围：纯前端 Web 应用（已部署 Cloudflare Workers 静态站），目标设备为儿童平板/手机（iOS Safari / Android Chrome 为主）。
> 原则：**优先使用设备/系统自带的 AI 模型**（端侧神经网络 TTS），不依赖任何云端付费 TTS。

---

## 0. 结论先行（TL;DR）

| 项 | 当前 | 目标 |
|---|---|---|
| 引擎 | Web Speech API（系统 TTS，质量随设备波动） | **Kokoro-82M 端侧神经网络 TTS**（主） + 系统神经音色（兜底） |
| 多音字 | 不可控，靠系统猜测 | **拼音驱动 G2P**：诗词用已标注拼音，通用文本用 `pinyin-pro` |
| 韵律/情感 | 仅全局 rate/pitch 黑客式调节，且分段 utterance 接缝明显 | 逐句/逐字时长控制（平仄长短、韵脚拖腔）+ 题材情绪预设 |
| 断句 | 整句一个 utterance，长句不可控 | 标点/句读分句 + Web Audio 流式拼接，句读分明 |
| 进度控制 | `pause/resume` 在部分浏览器失灵 | AudioContext 级暂停/继续/跳转，稳定可靠 |
| 离线 | 桌面 Chrome 实际走云端 | 模型一次下载后 100% 本地推理 |
| 体积 | 0 | 首次约 86MB（q4f16 量化），缓存后不再下载 |

**一句话选型**：以 **Kokoro-82M（kokoro-js，ONNX Runtime Web，WebGPU/WASM）** 作为端侧主引擎，彻底解决「机械感 + 多音字 + 不可控韵律」；保留并增强现有 **Web Speech API** 作为兜底与即时方案；模型文件**自托管到 Cloudflare（R2/CDN）**而非 HuggingFace（国内被墙）。

## 1. 平台可用 AI 语音能力调研与对比

本项目是浏览器内的 Web 应用，所谓「设备/系统自带的 AI 模型」在 Web 平台上只有两条路：**① 浏览器调用操作系统内置 TTS（Web Speech API）；② 在浏览器内运行神经网络 TTS 模型（ONNX Runtime Web / WebGPU）**。云端 TTS 因「需联网+计费+隐私」不符合本次要求，仅作备选提及。

### 1.1 候选能力一览

| 能力 | 音质 | 首响延迟 | 资源占用 | 离线 | 多音字控制 | 中文授权/限制 |
|---|---|---|---|---|---|---|
| **Web Speech API（系统音色）** | 中~较好（iOS Siri 类神经音色好，国产 Android Pico 差） | 低（~100–400ms） | 几乎为零 | 取决于系统（iOS/Android 本地；桌面 Chrome 走云端） | ❌ 不可控 | 免费，但 Android 部分浏览器**根本不支持** `speechSynthesis`（已踩坑） |
| **Kokoro-82M（kokoro-js）** | 中上（接近云 TTS 叙述级） | 模型加载后首个 chunk ~50–200ms | 模型 86MB(q4f16)/300MB(fp32)；推理 RAM 300–500MB | ✅ 100% 本地（模型缓存后） | ✅ 可通过拼音/音素输入精确控制 | Apache 2.0，可商用 |
| **Piper zh_CN（VITS）** | 中（清晰但偏「合成感」） | 加载后 ~100ms | 单音色 ~40–80MB；需 espeak-ng wasm 前端 | ✅ 本地 | ⚠️ 依赖 espeak G2P，多音字一般 | Apache/MPL，可商用 |
| **OS 神经音色（iOS Siri / Android 高质量）** | 好（最自然的一类） | 低 | 零（系统提供） | ✅ 本地 | ❌ 不可控 | 免费，但**Web Speech 不一定能选到**该类音色 |
| **云端 TTS（Azure/字节/阿里/讯飞）** | 优（最自然、含情感发音人） | 300–800ms（含网络） | 零端侧 | ❌ 需联网 | ✅ SSML phoneme | 按量计费、需密钥、隐私出域 |

### 1.2 关键事实（来自调研）

- **Kokoro-82M**：82M 参数，StyleTTS2+ISTFTNet 架构，24kHz，Apache 2.0。**支持普通话**（v1.0 起扩展至 8 语言/54 音色，含中文 `zf_001` 女声、`zm_010` 男声等）。量化 q4f16 约 **86MB**，fp32 约 300MB。通过 `kokoro-js` + `@huggingface/transformers`(Xenova) + `onnxruntime-web` 在浏览器运行，**WebGPU 比 WASM 快 2–10 倍**，流式合成首播延迟可压到 50–200ms。
- **致命约束**：HuggingFace 与多数境外 CDN **在中国大陆被墙**。本项目用户是中文儿童，**模型文件必须自托管到 Cloudflare（同域/同区域 CDN 或 R2）**，不能依赖 HF 在线拉取。
- **Web Speech 的现实坑**：国产 Android 浏览器 `window.speechSynthesis` 可能为 `undefined`（已确认有同类踩坑案例）；iOS 需用户交互后才能播放；`pause/resume` 在 Chrome 长期有 bug。

### 1.3 对比结论

- 要「自然度 + 多音字可控 + 离线 + 免费」四者兼得，**唯一现实的端侧方案是 Kokoro-82M**。
- Piper 中文质量偏弱、前端（espeak wasm）更重，作为**备选**。
- Web Speech 系统音色**保留为兜底/即时方案**（零下载、零延迟、覆盖不支持 WebGPU/WASM 或低端设备的浏览器）。

## 2. 现有朗读实现的问题根因分析

现有引擎全部在 `src/lib/speech.ts`，调度在 `src/lib/chant.ts` 与 `src/modules/poems/poemTrain.tsx`。逐条定位：

### 2.1 音色（timbre）—— 无选择、靠猜测
- `pickVoice()` 用名字关键字（`tingting`/`samantha`…）盲猜，命中率低；未区分「系统基础音」与「神经/高质量音」。
- 没有用户可选项，孩子只能听系统默认音，**iOS 可能拿到旧音、Android 可能拿到 Pico 机械音**。

### 2.2 语速 / 音调 —— 全局粗调，且被「分段 utterance」破坏
- `speak()` 给中文固定 `rate=0.78`、`pitch=1.15`；`speakChant()` 再按 `baseRate*rateMul` 逐片段覆盖。
- **核心病灶**：`speakChant` 把一句诗切成多个 `SpeechSynthesisUtterance`（平声段、仄声段、韵脚单字、停顿各一个）。**每个 utterance 都会重置语速/音高、插入不可控的起停间隙**，于是「抑扬顿挫」反而变成「一顿一顿的机械拼接」——这正是「缺乏自然度」的主因。

### 2.3 韵律 / 情感 —— 只可视化、没真正发声
- `chant.ts` 已算好平仄长短、韵脚拖腔、题材情绪（`MOOD_TABLE`），但注释明确写着：*「浏览器 speechSynthesis 无法逐字控调音高，故音高起伏仅在节奏条上呈现，实际发声仍走逐句 TTS」*。
- 所谓「有感情朗读」只是换了全局 rate/pitch/volume，**真实音频没有平仄起伏、没有韵脚拖长**。

### 2.4 断句 —— 只能整句，长句不可控
- `speakSequence` 按行朗读；`speakChant` 虽有分段，但分段目的是做「黑客式调速」，不是真正的语义断句。遇到长句/无标点文本会一口气读完。

### 2.5 多音字 —— 完全不可控 ⚠️
- Web Speech API 不接受拼音/音素输入，只能靠系统模型猜测。
- 诗词里大量多音字会读错，例如：`重`（chóng/zhòng）、`长`（cháng/zhǎng）、`行`（xíng/háng）、`思`（sī/sì）、`还`（hái/huán）、`看`（kàn/kān）。**项目数据 `DeepPoem.lines[].chars[].p` 已存正确拼音，但当前朗读根本没用上**——这是巨大浪费，也是升级的最大收益点。

### 2.6 中英混读 —— 单 utterance 跨语言易错位
- `speak()` 整个文本用同一 `lang`。若一句里混了英文单词（如 AI 讲解里的术语），系统可能用中文音来读英文，或反之。
- 字母/数字模块（`speakLetter`/`speakNumber`）是单独按 `en-US`/`zh-CN` 发的，但**同一句话中英混排时无语言切换**。

### 2.7 机械感的合成根因（总结）
1. 端到端是「拼接式系统 TTS」，本就偏机械（尤其 Android）；
2. 一句被切成多个独立 utterance，**接缝与重置破坏连贯性**；
3. 没有音素级输入，**平仄/韵脚/多音字信息全部丢失**；
4. 无神经声学模型，**自然度天花板低**。

## 3. 推荐方案与备选 + 取舍

### 3.1 推荐：Kokoro-82M 端侧主引擎 + Web Speech 兜底
- **主引擎 `KokoroEngine`**：`kokoro-js` 经 ONNX Runtime Web 在浏览器本地推理。
  - 解决机械感：神经声学模型，自然度显著高于系统拼接 TTS。
  - 解决多音字：以**拼音/音素作为输入**（诗词用 `chars[].p`，通用文本用 `pinyin-pro` 实时 G2P），精确控制读音。
  - 解决韵律：逐句合成、以 `speed` + 时域拉伸（WSOLA）控制平仄长短/韵脚拖腔；题材情绪映射到 `voice + speed + 微调`。
  - 解决断句：文本预处理分句后逐句合成，句读停顿由调度层精确插入。
  - 离线：模型一次下载缓存后，推理全程不出设备。
- **兜底 `WebSpeechEngine`**：沿用并增强现有实现（神经音色优选 + 音色选择 + 稳定性修复）。在以下情况自动切换：
  - 浏览器不支持 WebGPU 且 WASM 路径不可用/过慢；
  - 模型加载失败、推理抛错、或用户手动选「仅系统」；
  - 低端设备（RAM/存储不足）。

### 3.2 备选方案
- **Piper zh_CN**：若 Kokoro 中文音质/音色不满足，可换 Piper（更小单音色、清晰），但前端需 espeak-ng wasm、中文 G2P 一般，多音字收益下降。
- **系统神经音色优先（无下载）**：若用户强烈反对 86MB 下载，可只做「Web Speech 神经音色优选 + 拼音 G2P 提示」的轻量版——但 Web Speech 不接受拼音输入，**多音字仍无解**，仅提升音色，不推荐作为主方案。
- **云端 TTS 增值档（可选，非默认）**：未来可做「家长付费解锁更自然发音人」，但需后端代理密钥、按量计费，且出域隐私，本次不做。

### 3.3 取舍理由
- 用户明确要求「设备/系统自带 AI 模型」→ 排除云端。
- 要「专业级 + 多音字可控 + 离线」→ 唯一可行是端侧神经 TTS → Kokoro。
- 86MB 一次性下载对家长可接受（一次后永久缓存）；用 `q4f16` 量化 + 懒加载 + 同域 CDN 把代价降到最低。
- 兜底保证「任何设备都能出声」，符合幼儿产品「绝不允许点了没声音」的硬约束。

## 4. 集成架构设计

### 4.1 引擎抽象层（统一接口，便于降级）
```ts
// src/lib/tts/engine.ts
export interface TtsSegment { text: string; lang?: 'zh-CN' | 'en-US'; }
export interface TtsOptions {
  voiceId?: string; rate?: number; pitch?: number; volume?: number;
  emotion?: string;            // MOOD_TABLE 的 key 或 'auto'/'standard'
  onLine?: (index: number) => void;   // 逐句高亮（-1=结束）
}
export interface TtsController { cancel(): void; pause(): void; resume(): void; seekTo(index: number): void; done: Promise<void>; }
export interface SpeechEngine {
  readonly id: 'kokoro' | 'webspeech';
  isSupported(): boolean;
  /** 预热/加载模型；返回进度 0..1。WebSpeech 立即 resolve */
  load(onProgress?: (p: number) => void): Promise<void>;
  voices(): { id: string; name: string; lang: string }[];
  speak(segments: TtsSegment[], opts?: TtsOptions): TtsController;
}
```
- `createEngine(pref)`：按偏好与设备能力返回主引擎；运行期若主引擎抛错，由调度层捕获并切到另一引擎重放（**降级对调用方透明**）。
- 现有所有调用点（`speak`/`speakSequence`/`speakChant`）改为薄封装，内部路由到当前引擎，**UI 无需逐个改**。

### 4.2 模型加载与缓存
- **代码分包**：`kokoro-js`、`@huggingface/transformers`、`onnxruntime-web` 用 `import()` 动态加载，**不进首屏包**（避免拖慢首屏）。
- **模型托管（关键）**：把 `kokoro-q4f16.onnx` + `tokens.json` + `voices.bin` 放到 **Cloudflare R2**（同域 `https://xkxly.ccwu.cc/models/...`，全球 CDN、国内可达）。**绝不用 HuggingFace 在线地址**（被墙）。
  - 备选：放进 `public/models/` 走 Worker ASSETS，但会让每次部署多传 86MB、且占构建体积——仅作临时方案。
- **客户端缓存**：首次 `fetch` 模型后写入 **Cache API**（或 IndexedDB），之后直接读缓存；用 `Content-Type: application/octet-stream` + CDN 长缓存。
- **加载进度 UI**：首次播放弹出「正在准备小老师的声音… X%」进度条；后台预热的引擎不阻塞交互。
- **量化选择**：默认 `q4f16`（86MB）；高端设备可选 `fp32`（300MB，音质更好）。

### 4.3 文本预处理与分句
- **G2P（多音字根解）**：
  - 诗词：`DeepPoem.lines[].chars[].p` 已是正确拼音 → 直接拼成 Kokoro 期望的**拼音/音素序列**（P0 验证输入格式）。
  - 通用文本（AI 讲解、鼓励语）：用 `pinyin-pro`（项目已依赖）实时转拼音，开启异读字消歧（`multiple` + 词典/上下文）。
  - 中英混排：按字符语言切分，中文走拼音 G2P，英文直接保留拉丁字母（Kokoro 多语音色可混读）。
- **分句（断句）**：复用 `chant.ts` 的标点/句读切分逻辑，输出 `TtsSegment[]`；古诗词额外保留「行」边界以驱动逐句高亮。
- **韵律标注**：用 `analyzeChant()` 的平仄/韵脚结果为每个 segment 生成 `speed`/时长系数（见 4.5）。

### 4.4 流式合成与播放（Web Audio 管线）
```
预处理(G2P+分句+韵律) → 逐句 synth() → Float32 PCM
   → decodeAudioData → AudioBuffer → 入播放队列(Web Audio)
   → 首块就绪即播放（流式），后续块边生成边衔接
```
- 单一 `AudioContext`；`gainNode` 控音量；句子间由调度层插入精确停顿（句读）。
- 合成与播放解耦：合成线程产出 buffer，播放线程按队列衔接，**首音节延迟低、无整句等待**。
- 复用 `poemTrain.tsx` 已有的 `audioRef` 单例模式，避免反复创建 Audio 元素泄漏。

### 4.5 韵律/情感注入（让「有感情」真正发声）
- **平仄长短**：每句 `speed = base * (仄声多→略快 / 平声多→略慢)`；韵脚末字单独以更低 `speed`（拖腔）+ 可选 WSOLA 时域拉伸延长。
- **情绪预设**：`MOOD_TABLE`（思乡/边塞/山水/送别…）映射为 `{voiceId, speed, 微调}`；UI 显示「🎭 情绪基调 · XXX」沿用现有设计。
- **逐字可控（进阶）**：若需完全「依字行腔」，对单句 PCM 做 WSOLA 逐字时长重采样（按 `ChantToken.holdMs` 比例），实现真正「平长仄短」。P3 阶段做，P2 先以句级 `speed` 逼近。

### 4.6 进度控制（稳定可靠）
- 基于 AudioContext：`pause()→ctx.suspend()`、`resume()→ctx.resume()`、`seekTo(i)→断开当前源并从第 i 句重启`、`cancel()→断开+清空队列`。
- 比 Web Speech 的 `pause/resume` 可靠得多（避开 Chrome bug）。
- `onLine(i)` 仍用于逐句高亮，与播放队列索引对齐。

### 4.7 失败降级（对调用方透明）
```
try { ctrl = kokoroEngine.speak(segs, opts); await ctrl.done; }
catch (e) {
  console.warn('端侧引擎失败，降级系统音色', e);
  analytics('tts_fallback', { reason: e.name });
  ctrl = webSpeechEngine.speak(segs, opts);   // 同参数重放
}
```
- 加载失败、推理抛错、设备不支持 → 一律降级；降级本身再失败才静默（不吓孩子）。

## 5. 可调参数与用户设置项

### 5.1 引擎参数（开发者/高级）
| 参数 | 范围 | 默认 | 说明 |
|---|---|---|---|
| `voiceId` | 音色列表 | 温暖女声(kid-friendly) | Kokoro 中文音色 + 系统神经音色 |
| `rate` | 0.5–1.5 | 0.8 | 语速（幼儿跟读偏慢） |
| `pitch` | 0.7–1.3 | 1.0 | 音调（Kokoro 经 WSOLA；WebSpeech 直控） |
| `volume` | 0–1 | 1.0 | 音量 |
| `emotion` | auto/standard/7 种题材 | auto | 情绪风格 |

### 5.2 用户设置项（设置面板，落 zustand + localStorage）
- **朗读引擎**：自动（端侧优先→系统兜底）/ 仅系统 / 端侧优先。
- **音色**：下拉（如「甜甜姐姐 / 阳阳哥哥 / 系统默认」）。
- **语速**：滑块（慢↔快），实时试听。
- **音调**：滑块（低↔高）。
- **情感风格**：自动识别 / 标准 / 思乡·低回 / 边塞·苍凉 / 山水·清新 …（与 `MOOD_TABLE` 对齐）。
- **省流量模式**：关端侧模型，仅用系统音色（给存储/流量敏感用户）。
- 试听按钮：改任一项立即朗读示例句。

## 6. 性能与体积影响 + 优化建议

| 维度 | 影响 | 优化 |
|---|---|---|
| 首屏体积 | 几乎不增（引擎懒加载，不进首包） | `manualChunks` 已拆分 vendor；Kokoro 相关走动态 `import()` |
| 首播放延迟 | 首次需下载 86MB（仅一次） | 同域 CDN + Cache API；后台预热；进度条 |
| 推理性能 | WebGPU：RTF<0.3（Apple Silicon/新安卓）；WASM：RTF≈0.5–1.0 | 检测 WebGPU 优先；低端设备自动降级系统音色 |
| 内存 | 推理期 300–500MB | 合成完即释放；单句 buffer 不堆全篇 |
| 存储 | 模型缓存 ~86–300MB | 量化 q4f16；提供「清除模型」入口 |
| 网络/隐私 | 模型下载后零出网 | 自托管 Cloudflare，不依赖 HF |

**关键优化清单**
1. 模型自托管到 Cloudflare R2（国内可达），不用 HF。
2. `q4f16` 量化 + WebGPU 优先 + WASM 兜底。
3. 引擎代码动态分包，首屏零负担。
4. 首次进入后台预热模型（不阻塞交互），用 Cache API 持久化。
5. 提供「省流量/清除模型」开关，尊重低端设备与家长隐私。
6. 固定 `onnxruntime-web` 版本，避免 CDN 漂移。

## 7. 分阶段实施计划与验收标准

### P0 · 技术验证（2–3 天）
- 独立测试页跑通 `kokoro-js`：中文 `zf_001` 音色音质主观评测；WebGPU vs WASM 延迟测量。
- **验证关键风险**：Kokoro 中文能否以「拼音/音素」为输入精确控制多音字；确定拼音→Kokoro 输入格式的映射表。
- 产出：可行性结论 + 输入格式 spec + 目标设备 RTF 基线。

### P1 · 引擎抽象 + Web Speech 增强（2 天）
- 定义 `SpeechEngine` 接口，重构 `speech.ts` 为引擎模式（**向后兼容，UI 不破**）。
- 增强 WebSpeech 引擎：神经音色优选、`voices()` 暴露、修复 `pause/resume` 与「长时间闲置无声」bug。
- 设置项 store（engine/voice/rate/pitch/emotion）+ 基础设置面板。

### P2 · Kokoro 主引擎集成（4–5 天）
- 动态 `import` kokoro-js；模型自托管到 R2 + Cache API 持久化 + 加载进度 UI。
- G2P：诗词用 `chars[].p`，通用文本用 `pinyin-pro`。
- 流式 Web Audio 播放管线 + 暂停/继续/跳转 + `onLine` 高亮。

### P3 · 韵律与情感真正发声（3 天）
- 平仄长短、韵脚拖腔映射到句级 `speed`/时长；`MOOD_TABLE` → 音色+语速预设。
- （进阶）WSOLA 逐字时长重采样实现「依字行腔」。
- 中英混排分句与语言切换。

### P4 · 设置 UI + 健壮性 + 评测（3 天）
- 完整设置面板（试听、省流量、清除模型）。
- 降级健壮性、离线测试、性能调优（预热带宽/量化）。
- A/B 主观评测 + 客观指标验收。

### 验收标准
**主观（MOS，1–5 分，家长+儿童盲评）**
- Kokoro 主引擎 MOS ≥ 4.0（自然、亲切、适合儿童）；
- 对比当前 Web Speech 有明显「更自然、不机械」偏好（偏好率 ≥ 70%）。

**客观指标**
- 首音节延迟（模型已缓存）：< 800ms；
- 实时因子 RTF：WebGPU < 0.3 / WASM < 1.0（目标硬件）；
- 模型下载体积 ≤ 100MB（q4f16）；
- 多音字准确率（诗词测试集，如 重/长/行/思/还/看）：≥ 95%；
- 离线合成：模型缓存后**零网络请求**完成整首朗读；
- 降级成功率：100%（端侧失败时系统音色必出声）；
- 进度控制：`pause/resume/seek` 在 iOS Safari + Android Chrome 全部可用。

## 附录 · 关键风险与验证清单
1. **Kokoro 中文输入格式**：能否以拼音/音素输入精确控多音字 —— P0 必须验证。
2. **HF 被墙**：模型必须自托管 Cloudflare，不可用在线 HF 地址。
3. **WebGPU 覆盖**：iOS Safari 17+ / 现代 Android Chrome 支持；旧设备/部分国产浏览器不支持 → 靠降级兜底。
4. **内存峰值**：低端平板推理期可能 OOM → 监测 + 自动降级。
5. **Firefox 兼容**：Kokoro 在 Firefox 有兼容问题 → 默认走系统音色兜底。
6. **安卓 Web Speech 缺失**：部分浏览器 `speechSynthesis` 为 `undefined` → 端侧引擎必须能在这些环境独立工作（不依赖系统 TTS 兜底）。
